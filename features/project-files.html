The plan is a file, not an account

Three tools, one object: a .kaido file you can copy, diff, back up and read without the app.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

The three tools

ToolDoes
project_createCreates a project. Optional projectStart / projectEnd (ISO 8601) set the window that scheduling and violation checks are measured against.
project_openOpens a .kaido file. Reports formatVersion and whether a save would upgrade the file.
project_saveSaves to the open file, or acts as save-as when a path is given.

Why the format matters

The plan is plain JSON with a formatVersion field, currently 2. That single decision carries most of the properties people actually want:

  • It goes in the repository. Next to the code, reviewed in the same pull request, with one-line diffs when a date moves.
  • It outlives the tool. If this app disappears tomorrow, the plan is still a JSON document with a documented shape.
  • It is inspectable without permission. An agent, a script or a person with jq can read it. No export step, no API key.
  • It is local. No account, no sync, no server copy. The app's only unprompted network call is the update check.

What "formatVersion" buys you

When the schema changes, the app knows what it is reading and upgrades on save, reporting upgradedFrom once so the change is visible rather than silent. Older files open; newer files are not silently rewritten.

The project window is not metadata

Setting a start and an end date is what makes a task "outside the project window" detectable. Without a window, the violation checks have nothing to compare against, and the plan degrades into a list with dates attached.

Questions this page does not answer

Can I edit the file by hand?

It is plain JSON, so yes — and the app will load it. Keep the schema intact; the CLI and MCP tools are the safer path for structural changes.

Is there a sync service?

No. Put the file in whatever repository or backup you already trust.
