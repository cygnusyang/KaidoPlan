A delivery check you can run in five minutes

An agent that reports progress honestly can still leave you with a plan that no longer adds up. The check below does not ask anyone how it is going. It asks the plan.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

Why a status report is not a delivery check

A status report answers "what is done". A delivery check answers "when does this finish, and what would have to be true for that to change". The two diverge exactly when it matters: every task says complete, and the end date has still moved, because something that was supposed to finish first finished late, or a dependency was never written down, or a task was scheduled before its predecessor ended.

None of those are coding errors. They are arithmetic errors in the plan, and they are invisible in a chat transcript. So the check runs on the file, not on the narrative.

The four checks

1. Does the schedule compute at all?

kaidoplan schedule compute --file plan.kaido

This propagates the dependencies and returns each task's earliest and latest dates. If a dependency cycle exists, the schedule cannot be computed — which is the most useful possible failure, because it means the plan describes work that can never start.

2. Which chain sets the end date?

kaidoplan schedule path --file plan.kaido

Critical path and slack. Zero-slack tasks decide the delivery date; everything else has room. This is the answer to "what should I worry about", and it usually contains two or three tasks, not fifteen.

3. What does the plan admit is broken?

kaidoplan violations --file plan.kaido

Four classes come back, and each has exactly one correct response:

ViolationWhat it meansWhat to do
Dependency cycleThe plan says A waits for B and B waits for ABreak the cycle. Nothing downstream of it is real.
Deadline conflictA task finishes after a constraint or the project endMove the date, cut the scope, or move the constraint — decide deliberately.
Task outside the project windowA task starts before the project starts or ends after it endsEither the window is wrong or the task does not belong in this project.
Blocked chainWork that cannot proceed because an upstream item is stuckThis is the chain to escalate today, not the loudest task in the list.

4. Did the agent's write-back land?

kaidoplan status batch --file plan.kaido --json

Bulk status writes return per-entry success and failure. A failing entry does not stop the rest, which is the right behaviour and also the reason you have to read the output: partial success looks like success from a distance.

Reading the result honestly

Three outcomes, three different conversations:

  • No violations and a named critical path. The plan is internally consistent. Whether it is achievable is a different question, and the answer is not in the file.
  • Violations that were already there last week. Nothing has changed, which means the check has become ritual. Fix one, then re-run.
  • Violations appeared after a write-back. An agent updated status without updating dates. This is the common case, and the reason status write-back and date review belong in the same loop.
The one-sentence version

Run the check whenever an agent changes the plan, and treat a violation the same way you treat a failing test: not as bad news, but as information that arrived early enough to be useful.

Doing it on a real repository

The plan is a file in your repo, so the check can be part of the pull request you were going to open anyway: run violations, paste the output, and if it is non-empty the change is not ready. That is the entire integration — no dashboard, no webhook, no account.

If you want the same four checks without a terminal, the app's workbench shows violations inline and the critical path highlighted in the Gantt chart. Same numbers, different surface.

You can also install a ready-made skill from SkillHub and run the same checks:

skillhub install kaidoplan-delivery-check

Questions this page does not answer

How is this different from a burndown chart?

A burndown chart plots completed work against time. It cannot see that a dependency was never recorded, or that a completed task finished after the task that depended on it. The four checks read the dependency graph, not the totals.

Does the check need the Pro licence?

No. Computing the schedule, reading the critical path and listing violations are read operations and work on the free tier. Only writing status back from an agent needs Pro.
