Set up a KaidoPlan plan in ten minutes

Most planning failures are not tool failures. They start with a plan that has no end date, no dependencies and no way to tell whether the arithmetic still holds. This is the shortest path to a plan that does.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

Before you start

You need macOS 14 or later and about ten minutes. No account is involved: the app never asks you to sign in, and the plan is a file on your disk. The download is a 30-day full-feature trial; when it ends the app drops to the free tier rather than switching off.

brew install --cask cygnusyang/kaidoplan/kaidoplan
brew install cygnusyang/kaidoplan/kaidoplan-cli

The CLI is optional for planning in the GUI, but you will want it for the checks below and for anything an agent does on your behalf. If you would rather not use Homebrew, the same builds are on GitHub Releases.

1. Give the project a window before you add any work

Create a project and set a start and an end date. This is not decoration: the window is what every violation check is measured against. A task that finishes after the project end is a violation, and it cannot be reported if the project has no end.

The plan is stored as a single .kaido file — plain JSON, formatVersion 2. You can put it in the repository next to the code, diff it in a pull request, or read it with jq. It is not a database and it is not synced anywhere.

2. Add the work as a WBS, not as a list

Tasks, groups and milestones, each with an effort estimate. The distinction that matters: a list records what exists, a WBS records what depends on what. If two tasks can run in parallel, say so; if they cannot, the dependency is the only thing that will stop the schedule from quietly compressing into a fiction.

If you already have the breakdown in another tool, import it instead of retyping it. wbs_import takes a nested task tree and turns it into the plan.

3. Connect the dependencies

A finish-to-start dependency with an optional lag covers most real projects. Constraints — start no earlier than, finish no later than — cover the rest: a review that cannot begin before a date, a demo that cannot slip past one.

When you are done, every task should have exactly one honest answer to "what has to finish before this starts". Tasks with no predecessor are the start of a chain, and chains are what the next step computes.

4. Run the check before you trust the dates

kaidoplan schedule compute --file plan.kaido
kaidoplan schedule path --file plan.kaido
kaidoplan violations --file plan.kaido

The first command propagates dependencies and returns each task's earliest and latest dates. The second returns the critical path: the chain whose total slack is zero, which is the only chain that decides your delivery date. The third lists violations — dependency cycles, deadline conflicts, and tasks scheduled outside the project window.

Run all three after any change that touches dates. The result you are looking for is boring: no violations, and a critical path you can name out loud.

5. Connect the agent that will actually write the code

In the app, open the MCP service panel. Each supported client — Claude Desktop, Claude Code, Cursor, Codex and WorkBuddy — has one switch. Flipping it writes only the mcpServers.kaidoplan key into that client's configuration and leaves the rest of the file byte-identical, so your existing MCP servers and formatting survive. Turning it off removes the same key.

The service listens on the loopback address only, and every request has to carry the token shown in that panel. Only folders you authorized there are reachable.

Reading the plan works on the free tier. Writing to it — task status, actual dates, new tasks — is the Pro feature, because a plan that an agent can edit without limits is a plan nobody reviewed.

6. What "set up" actually means

  • The project has a start and an end date, and both are real.
  • Every task has an owner-by-intent, an effort estimate and its predecessors.
  • violations returns nothing.
  • You can name the critical path without opening the app.
  • One agent is connected, and you know whether it can write.

That is the whole setup. It is deliberately smaller than a project management methodology, because the failure mode it addresses is narrow: an agent reports every task done, and the date moved anyway.

Questions this page does not answer

Do I need the Pro licence to plan?

No. The GUI workbench — WBS, dependencies, Gantt, critical path, validation, progress tracking — is in the free tier, and so is AI read access. Pro ($9.99/year) adds AI write-back and unlimited delivery-report exports.

Where does the plan live?

Wherever you save the .kaido file. There is no account, no sync and no server copy; the app's only unprompted network call is the update check.

Can I keep using my current task tracker?

Yes, as long as you accept that the tracker will not tell you which chain sets the end date. KaidoPlan is the schedule layer, not a second inbox.
