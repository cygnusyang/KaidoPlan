How do I keep a project plan in sync across Claude Code sessions?

Short answer: stop keeping the plan in the conversation. Put it in a file, give the agent a documented way to read and write it, and recompute the schedule after every write.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

Why sessions drift

Each Claude Code session starts with whatever context it was given and ends with a transcript. A plan that lives inside that transcript is lost or partially summarised at the boundary, so the next session rebuilds it from prose — and rebuilds it slightly differently. Two sessions later, two versions of the plan exist and neither is authoritative.

The fix is not a better summary. It is separating the plan from the conversation:

  1. A file owns the plan. Not a chat, not a scratchpad. One file in the repository, with a schema, that outlives every session.
  2. The agent reads it at the start of a session. One tool call or one cat, not a hand-written recap.
  3. The agent writes to it explicitly. Status, actual dates and new tasks go through defined operations rather than a paragraph asking a human to update a spreadsheet.
  4. Dates get recomputed after the write. The reason to do 1–3 at all: a write that changes a date can create a conflict, and only a recomputation will say so.

What this looks like with KaidoPlan

The plan is a single .kaido file — plain JSON, formatVersion 2 — so a session can read it with nothing installed. With the app running, an MCP server exposes 21 tools over the same file: task_list and project_summary to read, status_update and status_batch_update to write back, schedule_compute and violations_list to check the arithmetic afterwards. The CLI covers the same ground when the app is closed.

# start of session
kaidoplan project summary --file plan.kaido
# after the agent reports progress
kaidoplan status batch --file plan.kaido --json
kaidoplan violations --file plan.kaido

Because the file is in the repository, the plan's history is the commit history. A date that moved is a diff you can review, not a claim you have to take on trust.

The parts that are easy to get wrong

  • Letting the agent invent dates. An agent that both plans and executes will optimistically compress durations. Keep the estimates human-owned.
  • Skipping the recompute. A status write without a schedule recompute is how a plan accumulates silent contradictions.
  • Keeping a second copy in the handoff file. Two sources of dates diverge; the file that gets opened more wins.

Questions this page does not answer

Does it work without the app running?

Yes for reading and writing the file with the CLI, and for any tool that can parse JSON. The MCP server is the app's own surface and needs the app running.

Can several sessions use the plan at once?

Sequentially, yes — each write lands in the file. Concurrent writers are not coordinated, so treat the plan like a code file being edited: one session at a time.
