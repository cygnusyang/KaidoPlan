How do I keep a project plan in sync across Claude Code sessions?

Short answer: stop keeping the plan in the conversation. A project file, a documented read and write path, and a recompute after every write. The hard part is not the pattern, it is that the plan is a single-writer file and two sessions are two writers.

Updated 2026-11-17 · by cygnus, the developer of KaidoPlan

What a session boundary actually destroys

A session does not lose the plan in one event. It loses four specific things, and each one is small enough that its absence looks like normal working state:

  • Which tasks are done, by identifier. The transcript says "the API is basically finished". The plan says tasks 4A1C and 7D02 are done and 9B44 is in_progress with progress: 0.6. Only the second can be written back.
  • When each one completed. A status flag has no time. Without a completion timestamp, nothing downstream can check whether the client work started before the endpoint existed — the exact conflict a status report cannot see.
  • Why the edges exist. "The client goes after the API" survives a summary. "The acceptance test is blocked on the migration, which is blocked on the schema freeze" usually does not, and that second chain is the one that sets the date.
  • Whether the dates still add up. The plan that was consistent at 14:00 is not necessarily consistent after a session moves two tasks. Nothing in the transcript recomputes.

So the next session does not resume the plan. It reconstructs one from a lossy projection of it, and two reconstructions of the same prose do not agree. Nothing errors. The project simply acquires a second, slightly different schedule that nobody is maintaining.

The pattern: make the plan unreachable from the summary

  1. A file owns the plan. One file in the repository, with a schema and a format version. Not a scratchpad, not a per-session markdown table.
  2. The session reads it first, mechanically. One command, not a hand-written recap paragraph that the agent may or may not have been given.
  3. Progress is written through operations, not prose. Status goes in as data with a completion time, because a paragraph asking a human to update a spreadsheet is not a write path.
  4. The schedule is recomputed after the write. This is the step that justifies the first three: a write that changes a date can create a conflict, and only a recomputation will report it.

The loop, with real commands

In KaidoPlan the plan is a single .kaido file — plain JSON, formatVersion 2, keys sorted, one task object per entry. A session can read it with cat and nothing installed.

# 1. start of session: what is the state, what is the date
kaidoplan project summary --file plan.kaido
kaidoplan task list --file plan.kaido --json

# 2. after the agent reports progress: write a batch file
cat > updates.json <<'JSON'
[{"taskID":"4A1C","status":"done","progress":1},
 {"taskID":"9B44","status":"in_progress","progress":0.6}]
JSON
kaidoplan status batch updates.json --file plan.kaido

# 3. the step everyone skips
kaidoplan schedule compute --file plan.kaido
kaidoplan violations --file plan.kaido

Two details matter more than they look. status batch returns a per-entry result: a bad identifier rejects that line and leaves the rest of the batch applied, so a partial write is visible rather than silent. And task identifiers accept a unique prefix, which is what makes a batch file practical to have an agent produce.

With the app running, the same three steps are available as MCP tool calls (project_summary, status_batch_update, schedule_compute, violations_list) over stdio or the loopback endpoint. The CLI and the app are the same engine, so the two surfaces cannot disagree about the date.

Two sessions at once: the honest limitation

The file has no lock. Two sessions writing at the same time is two writers on one document, and the last save wins — including its stale copy of everything it did not touch.

Git does not save you here either, and it is worth saying why rather than implying version control solves it. The writer normalises the whole document on every save: keys are sorted, empty arrays are still emitted, and the project's updatedAt changes each time. A merge of two branches therefore conflicts on the file as a whole far more often than on the two tasks that actually differ. Stable task UUIDs stop an identity from being duplicated; they do not make the text merge cleanly.

The rule that works is boring: one writing session at a time per plan file. Parallel sessions can read freely — reads are cheap and they are how you avoid guessing — but writes get serialised. If you need isolation for a risky change, copy the file, work on the copy, and diff the two plans before you accept one.

What the file in the repository buys you

  • The plan's history is the commit history. A date that moved is a diff with a timestamp and a reason, not a claim to take on trust.
  • The session's claim becomes checkable. "Everything is done" is a sentence; git diff over the plan shows which identifiers changed and whether any dependency was added to make the schedule close.
  • Handoff stops being a document. There is no separate HANDOFF.md to keep in step, because the state the next session needs is the file it already opens.

Failure modes, in the order they appear

  • The agent invents dates. An agent that both plans and executes compresses durations, because "how long will this take" is answered optimistically by default. Keep estimates human-owned; let the agent own execution and reporting.
  • The recompute is skipped when nothing "seems" to have changed. A status write moves a completion time, which can pull a successor earlier and shorten the critical path. Fifty percent of plan corruption is one skipped recompute a day for a week.
  • A second copy lives in the handoff file. Two sources of dates diverge, and the one that gets opened more often wins — which is not the one that is correct.
  • Status is written as one big update at the end of the session. Batch it per work unit instead: a batch at the end of a long session is a batch written from memory, and memory is the thing you were trying to stop relying on.

Questions this page does not answer

Does it work without the app running?

Yes for reading and writing the file with the CLI, and for any tool that can parse JSON. The MCP server is the app's own surface and needs the app running.

Can several sessions use the plan at once?

Sequentially, yes — each write lands in the file. Concurrent writers are not coordinated, so treat the plan like a code file being edited: one session at a time.
