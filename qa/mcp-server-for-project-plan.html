Is there an MCP server for a project plan?

Yes — KaidoPlan has one built in. 21 tools over stdio or a loopback endpoint, covering tasks, dependencies, resources, baselines, scheduling and violation checks. Every write tool persists on its own; there is no save step to forget.

Updated 2026-11-17 · by cygnus, the developer of KaidoPlan

What MCP actually buys over parsing the file

The plan is already plain JSON, so an agent could read it with cat and write it with a text editor. That works for reading and is a bad idea for writing, for three reasons that have nothing to do with convenience:

  • Writing a consistent document is harder than reading one. A status change also moves the project's updatedAt, may need to record a completion time, and may invalidate dates downstream. Hand-editing JSON gets the field right and the consequences wrong.
  • A tool call can fail loudly. task_update with an unknown identifier returns an error. A careful string edit with the wrong UUID returns a file that parses perfectly and contains a dependency pointing at nothing.
  • Some answers are computed, not stored. The critical path is not a field in the file. An agent reading the JSON can see durations and edges and still get the chain wrong — the schedule engine cannot, because it is the thing the app's Gantt chart also calls.

That last point is the design constraint worth stating: the CLI, the MCP server and the window are the same engine. A command-line answer and the highlighted chain in the chart cannot disagree, because there is one implementation.

Client setup is one switch per client — Claude Desktop, Claude Code, Cursor, Codex and WorkBuddy — and the switch writes only the mcpServers.kaidoplan key into that client's configuration, leaving the rest of the file byte-identical. The app binary can also run as a stdio server directly (--mcp-stdio), so a client can start it without a separate CLI install.

A session, end to end

What the tool surface looks like when an agent is actually working. Four calls, in this order, and the fourth is the one that is always skipped:

  1. project_open with the file path. Returns formatVersion and whether the file will be upgraded on the next save — worth reading before you let an older client write to a newer plan.
  2. task_list filtered by parent, or project_summary's CLI equivalent for the aggregate. This is the read that replaces the recap paragraph.
  3. status_batch_update with an array of task IDs, statuses and progress. Returns per-entry success and failure: one bad identifier rejects that entry and leaves the rest applied, so a partial write is visible rather than silent.
  4. schedule_compute, then violations_list. The recompute is what turns "I marked it done" into "the date is still valid, or it is not".

Every write tool persists to disk on its own. project_save exists for explicit saves, save-as, and retrying after a saved:false result — it is not a step the agent has to remember in the normal loop.

The security model, in three lines

  • Loopback only: the endpoint listens on 127.0.0.1, never the LAN or the internet.
  • Every request carries a token the app generates locally and shows in its panel.
  • Only folders you authorised in that panel are reachable; anything else is refused, before the file is opened.

The server is on by default since v3.4.0, on the loopback address with a token. Turning it off in the panel stops access immediately, and a previous explicit off setting is not overridden by that default change.

Read versus write

Reading a plan through the server — listing tasks, computing the schedule, listing violations — needs no licence at all. Writing status, actual dates, edges or new tasks back into the plan requires a Pro entitlement, which the 30-day trial grants in full. The split is not arbitrary: the write tools are the operations that can move a delivery date. An agent that can silently rewrite edges can silently rewrite the answer you report to a client.

If you would rather not add an MCP client at all, the CLI exposes the same operations from a shell, and the file is readable JSON. Nothing about the workflow depends on MCP; it is one of three ways in.

What it does not do

  • No remote access. The endpoint is loopback-only by design, so the agent has to run on the same Mac. A hosted agent cannot reach it, and that is the trade for not having an authentication story to get wrong.
  • No multi-user coordination. Two agents writing at once is two writers on one file; the last save wins, including its stale view of everything it did not touch. Serialise the writers.
  • No partial-file access. There is no "give the agent only task 12". It gets the plan it opened, which is why the folder authorisation list matters more than the token.
