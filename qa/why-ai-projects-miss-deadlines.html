Why do AI-assisted projects still miss deadlines?

Because writing code faster does not shorten the chain that decides the end date — and it makes the plan look healthy while that chain stays exactly as long as it was.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

1. The estimate was the agent's

An agent asked how long a task will take answers with an average case and no memory of the last time this class of task went wrong. Multiply that optimism across forty tasks and the plan is short before any work starts. Speed does not fix an estimate, it just makes the resulting slip more surprising.

2. Dependencies lived in prompts

If the order was communicated in a message instead of recorded in a graph, nothing enforces it. Work starts early, finishes after the thing that needed it, and every individual status is true.

3. Integration was treated as a task at the end

Integration, review and acceptance are where compression goes to hide. They are also the tasks most likely to be estimated at zero because they feel like a formality. A plan without them looks a week shorter and is a week wrong.

4. The wrong tasks were being watched

A daily report over forty green tasks trains everyone to look at volume. The delivery date is set by the zero-slack chain, which is usually two or three tasks and rarely the ones discussed in standup. Optimising the visible set feels productive and moves nothing.

What actually helps

  • Human-owned estimates, agent-owned execution. The agent writes code; the person who has shipped before sets the duration.
  • A dependency graph with real edges, so the schedule can be computed rather than asserted.
  • The four checks after every change: compute, critical path, violations, and confirmation that write-back landed.
  • Baselines, so "we slipped" is measured against a frozen schedule rather than a remembered one.

None of this makes the project faster. It makes the slip visible on the day it happens instead of the week it becomes undeniable — which is the only window in which a deadline can still be protected.

Questions this page does not answer

Does the tool shorten the critical path?

No. It tells you which chain sets the date so you can decide what to cut or parallelise. The decision stays yours.

Is this a scheduling problem or a communication problem?

Both, but the scheduling error is the one that cannot be argued with. That is why it is worth computing first.
