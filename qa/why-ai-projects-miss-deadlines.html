AI-assisted projects miss deadlines — and the arithmetic that catches it

Every task says done. The agent's summary says done. The pull requests are merged. And the delivery date has moved anyway.

Updated 2026-11-09 · by cygnus, the developer of KaidoPlan

"Done" is a property of a task. The delivery date is a property of a graph.

This is the most common failure in AI-assisted projects, and it is almost never a coding failure. Nobody lied, nobody slacked off, and no story was misreported. The status report and the schedule are describing two different objects, and they were never required to agree.

A task can be genuinely, verifiably complete and still ruin the date, because the date is produced by a chain of predecessors — and a chain does not care how green its individual nodes are.

Failure 1: the finished task that finished too late

Agents execute in the order they are asked, which is not always the order the plan implies.

Suppose server work finishes on the 6th, and client integration began on the 4th. Both statements can be true. Nothing in a task list objects, because a task list has no concept of one task having to precede another. A schedule does: it reports the pair as a date conflict, and it does so on the 4th, not on the 20th when someone asks for a date.

This is the single most valuable property of putting dates and edges in the same object. The contradiction becomes an error message instead of a surprise in a client call.

Failure 2: the dependency was never written down

Most plans record tasks and dates and stop there. Without an edge between two tasks, the data model has no way to express "the acceptance test cannot start before the API exists."

So the schedule compresses. The computed finish date comes out earlier than reality, the plan looks healthy, and it keeps looking healthy right up to the week the gap becomes undeniable. The information was never missing from the project — it was missing from the artifact.

A useful test for any tracker: can you express "B cannot start until A finishes" such that a machine will complain when that is violated? If the answer is "we agreed on that in Slack," you have a plan that cannot be checked.

Failure 3: the estimate was never yours

Ask an agent how long a task will take and you get an average case, with no memory of the last time this class of task went wrong. The agent is not being optimistic on purpose; it has no prior to be pessimistic with.

Across a plan of forty tasks, that bias does not average out. It compounds, because every task inherits the same missing memory. Speed then makes the outcome worse, not better: the work arrives faster, the slip arrives just as fast, and it is more surprising because everything felt productive.

The division of labour that survives contact with reality is boring: the agent writes the code, the person who has shipped before sets the duration. Not because humans estimate well, but because a human estimate carries the memory of previous failures and can be argued with in review.

Failure 4: integration, review and acceptance get estimated at zero

They are where schedule compression goes to hide. They also feel like formalities, so they get zero days — or they get dropped entirely because "the tasks are the work."

A plan without them looks a week shorter and is a week wrong. If your plan has no explicit task for review and acceptance, you have not omitted overhead; you have moved it into the part of the timeline nobody is measuring.

Failure 5: you are watching the wrong tasks

A daily report over forty green tasks trains everyone to look at volume. But the delivery date is set by the zero-slack chain — usually two or three tasks, and rarely the ones discussed in standup.

This is why status meetings feel productive and move nothing. Optimising the visible set is satisfying; only the critical path changes the date. If you cannot name the chain that sets your end date, you are managing a list, not a schedule.

A worked example

Four tasks, dates included, small enough to check by hand:

TaskDatesStatus
API designends Nov 1done
Server implementationends Nov 6done
Client integrationstarts Nov 4; predecessor ends Nov 7date conflict
Joint acceptancecritical path, 0 days slackblocks the end date

Three of four tasks are green. Two problems are visible in the table and invisible in a status report:

  1. Client integration starts on Nov 4 against a predecessor that ends Nov 7 — three days of work running before the thing it depends on exists.
  2. Joint acceptance sits on the zero-slack chain. Any day it moves, the delivery date moves one-for-one.

Neither is a coding error. Both are arithmetic errors in the plan, and both are cheap to fix on Nov 4 and expensive to explain on Nov 20.

The check that catches all five

You do not need a methodology. You need four operations run against the plan data after every change that touches dates:

# 1. Does the schedule compute at all? Early/late dates per task.
kaidoplan schedule compute --file plan.kaido

# 2. Which chain sets the end date? Critical path and slack.
kaidoplan schedule path --file plan.kaido

# 3. What does the plan admit is broken?
kaidoplan violations --file plan.kaido

# 4. Did the agent's status write-back actually land?
kaidoplan status batch --file plan.kaido --json

Step 3 returns four classes of problem, and each has exactly one honest response:

ViolationWhat it meansWhat to do
Dependency cycleA waits for B and B waits for ABreak the cycle. Nothing downstream is real.
Deadline conflictA task finishes after a constraint or the project endMove the date, cut scope, or move the constraint — decide deliberately
Task outside the project windowStarts before the project starts or ends after it endsEither the window is wrong or the task belongs elsewhere
Blocked chainWork that cannot proceed because an upstream item is stuckEscalate this chain today, not the loudest task in the list

The result you are looking for is boring: no violations, and a critical path you can name out loud. If you cannot say which chain sets your date, the check has not been done — it has been performed.

One detail worth internalising: bulk status writes should return per-entry success and failure, and they should not abort on the first failure. That is correct behaviour for a long list, and it is exactly why you have to read the output. Nine of ten entries landing looks like success from a distance.

Make it a failing test, not a ritual

A schedule check that lives in a weekly meeting decays into ritual within a month. A schedule check that lives in CI does not.

If the plan is a file in the repository, the check can be part of the pull request you were going to open anyway: run violations, paste the output, and if it is non-empty the change is not ready. No dashboard, no webhook, no account. When it passes it costs nothing, and when it fails you learn about a dependency cycle at commit time instead of at delivery time.

The same reasoning applies to the "done" definition. Make done mean done, and the plan recomputed — not as a slogan, but as the literal gate. Writing status through the tool surface rather than in prose matters here, because the completion time is what a conflict check needs; "done" as a boolean is enough for a burndown and useless for a schedule.

What none of this fixes

This check does not shorten your critical path. It tells you which chain sets the date so you can decide what to cut, parallelise, or renegotiate. The decision stays with you.

It does not fix a bad estimate either — a plan can be internally consistent and still unachievable. Consistency is the cheap half: it is the only half you can compute.

And it does not replace a project manager, a standup, or a conversation with a client. It makes the slip visible on the day it happens instead of the week it becomes undeniable, which is the only window in which a deadline can still be protected.

Questions this page does not answer

Does the tool shorten the critical path?

No. It tells you which chain sets the date so you can decide what to cut or parallelise. The decision stays yours.

Is this a scheduling problem or a communication problem?

Both, but the scheduling error is the one that cannot be argued with. That is why it is worth computing first.
