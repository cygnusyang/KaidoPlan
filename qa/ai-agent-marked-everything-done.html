The agent marked every task done — why did the deadline still slip?

Because done is a property of a task, and the delivery date is a property of a graph. Nobody was lying; the two never had to agree.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

Three ways a finished list produces a late project

1. A task finished after the thing that depended on it started

Agents execute in the order they are asked, which is not always the order the plan implies. Server work finishes on the 6th, client integration began on the 4th, and both statements are true. Nothing in a task list objects, because a task list does not know that one had to precede the other. A schedule does: it reports the pair as a date conflict.

2. The dependency was never written down

Most plans record tasks and dates and stop there. Without an edge between two tasks, the schema has no way to say "the acceptance test cannot start before the API exists" — so the schedule compresses, the finish date looks earlier than reality, and the project appears healthy right up to the week it becomes obvious.

3. The work that slipped is not on the visible path

Fifteen tasks are green. The two-day delay is in a task nobody watches because it looks small. It is on the critical path, so it moves the end date one-for-one. Everyone optimises what is visible; the date is set by what is on the zero-slack chain.

The check that catches all three

kaidoplan schedule compute --file plan.kaido
kaidoplan schedule path --file plan.kaido
kaidoplan violations --file plan.kaido

Computation gives real dates from the graph. The critical path names the chain that decides the end date. Violations list the conflicts, cycles and out-of-window tasks that a status report cannot see. Run them after every write-back and the three failures above stop being surprises.

What to change in the process

  • Make "done" mean "done, and the plan recomputed".
  • Have the agent write status through the tool surface instead of telling you about it — status_update records the completion time, which is what a conflict check needs.
  • Keep a baseline before each delivery push, so "slipped" is measurable against a frozen schedule rather than a memory.

Questions this page does not answer

Does the app edit the plan automatically?

Only when an agent or you call a write tool, and only with a Pro licence after the trial. Nothing is rewritten behind your back.

Can I see which task caused the slip?

Yes — the critical path plus the violation entry identifies the tasks with zero slack and the pair whose dates disagree. That is the audit trail, and it is why the plan is kept as a file.
