The agent marked every task done — why did the deadline still slip?

Because done is a property of a task, and the delivery date is a property of a graph. Nobody was lying; the two never had to agree.

Updated 2026-11-16 · by cygnus, the developer of KaidoPlan

A status report is not a schedule

The report answers "what is done". The delivery date is computed from edges and durations. When only the first object is maintained, the second one drifts — silently, because nothing compares them.

The useful abstraction is that done has two forms: a boolean a burndown chart can consume, and a timestamp a conflict check can consume. AI-assisted projects usually keep only the boolean.

Why the boolean is not enough

  • It cannot contradict anything. "Task 14: done" is compatible with every possible date. A date conflict needs a completion time and a predecessor's end time; a boolean supplies neither.
  • It hides the order. Agents execute in the order they are asked, which is not always the order the graph implies. Server work finishes on the 6th, client integration began on the 4th, and both statements are true. A task list has no concept of one task preceding another, so nothing objects.
  • It decays in prose. When status arrives as a paragraph — "finished the API work, moved on to the client" — the numbers go through a human transcription step, and transcription is where the completion time gets rounded to "yesterday".

The three checks that turn a report into arithmetic

kaidoplan schedule compute --file plan.kaido
kaidoplan schedule path --file plan.kaido
kaidoplan violations --file plan.kaido

The first produces real dates from the graph. The second names the chain that sets the end date. The third lists what the plan admits is broken: date conflicts, dependency cycles, tasks outside the project window, and blocked chains.

The result you want is boring — no violations, and a critical path you can say out loud. If you cannot name the chain that sets your date, the check has been performed, not done.

Recording status instead of reporting it

The single change that makes the checks possible: the agent writes status through the tool surface rather than narrating it.

kaidoplan status batch --file plan.kaido --json

Two properties matter in that call, and both are easy to get wrong:

  • Per-entry success and failure. A long batch should return which entries landed and which did not, and it should not abort on the first failure. That is correct behaviour, and it is exactly why you have to read the output: nine of ten entries landing looks like success from a distance.
  • A completion time, not just a state. The timestamp is the input a conflict check needs. "Done" as a boolean is enough for a burndown and useless for a schedule.

The audit trail you already have

If the plan is a file in the repository, the plan's history is the commit history. A date that moved is a diff someone can review, not a claim you have to take on trust. Two habits follow:

  1. Make done mean done, and the plan recomputed — as a literal gate, not a slogan.
  2. Take a baseline before each delivery push, so "we slipped" is measured against a frozen schedule instead of a remembered one.

What this does not do

It does not shorten the critical path, and it does not repair a bad estimate — a plan can be internally consistent and still unachievable. It makes the slip visible on the day it happens rather than the week it becomes undeniable, which is the only window in which a deadline can still be protected. Questions this page does not answer

Does the app edit the plan automatically?

Only when an agent or you call a write tool, and only with a Pro licence after the trial. Nothing is rewritten behind your back.

Can I see which task caused the slip?

Yes — the critical path plus the violation entry identifies the tasks with zero slack and the pair whose dates disagree. That is the audit trail, and it is why the plan is kept as a file.
