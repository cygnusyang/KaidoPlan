How do I break an AI coding project into a WBS?

Break it down by what can be checked without reading the code. The unit is not a phase and not a file — it is the smallest piece of work whose completion is a fact rather than an opinion.

Updated 2026-11-17 · by cygnus, the developer of KaidoPlan

The wrong unit, and why it feels right

Standard WBS advice divides by activity: design, build, test, ship. For a human team that is a reporting structure — it maps to who reports to whom and what a status meeting can ask about.

For a project executed by an agent it is close to useless, for one reason: an agent produces no social signal that a phase has ended. There is no "the build phase feels done". There is a diff, a failing test, and a file that either parses or does not. So the unit of breakdown has to be something a machine and a reviewer can both check:

A task is well-sized when someone can say whether it is done without reading the implementation.

"Improve the importer" fails that test. "Import a 1PUX export with attachments and reconcile the item count against the file" passes it: the item count either matches or it does not.

What that looks like in practice

A single feature — CSV import — broken down this way. Every row has a check and a duration, which is the whole point; the check is what stops the task drifting, and the duration is what lets the plan compute a date.

Six days of work, seven tasks, and each one is a yes-or-no question afterwards. Notice what the breakdown did not do: it did not create a task called "backend" that swallows four of these and reports 80% for a week.

The shape, in order

  1. Acceptance criteria first. What is observably true on the delivery date. Written before the tasks, because it decides what the tasks are.
  2. Chains that end at a milestone. Group tasks so each group produces one checkable milestone, then connect the milestones. A milestone is where someone other than the author has to agree — that is what makes it worth having.
  3. Integration and review as their own tasks. They are the first things eaten when a plan is compressed, they are routinely estimated at zero because they feel like a formality, and their disappearance is what a late project looks like from a week away.
  4. A duration on every task. Coarse is fine — half a day, a day, three days. Absent is not: without durations there is no schedule to compute, only a list with a hopeful date stapled to it.

The two fields that make it schedulable

A WBS on its own is a tree. A tree has no dates. What turns it into a schedule is edges and durations, and most of the design work is in the edges, because an edge is a claim about the world:

  • Parser cannot start before the contract is written (finish-to-start).
  • Upload endpoint cannot start before the migration applies.
  • Reconciliation needs both the endpoint and the parser.

If you cannot state the edge in that form — "X cannot start before Y finishes" — it is probably not an edge. "Related to" is not a dependency, and adding it makes the critical path fiction.

If the breakdown already exists as a nested outline, import it rather than retyping. The CLI takes a JSON tree of title, optional kind (task, group, milestone), durationDays or effortHours, and children:

kaidoplan wbs import wbs.json --file plan.kaido
kaidoplan schedule compute --file plan.kaido
kaidoplan violations --file plan.kaido

Import carries structure, kinds and estimates. It does not carry dependencies — there is no edge in the JSON, by design, because an outline does not know them. Adding the edges is the next step and the one that cannot be automated from a document.

The failure to avoid

An agent asked for a WBS returns sixty tasks in a flat list: no groups, no edges, no durations, phrased as verbs. It reads as thorough work and it is unusable, in a specific way:

  • Nothing can be scheduled. No durations means no forward pass; no edges means no chain; no chain means no date.
  • Nothing can be checked. "Implement authentication" is not done or not done, it is "mostly there".
  • The volume creates false confidence. Sixty items looks like a plan understood in detail. It is a transcript of what the agent would do next, written in the grammar of a plan.

The correction is not to ask for fewer tasks. It is to ask for the check alongside each one, then delete every task whose check you cannot state. In practice that removes about a third of them and the remaining forty are schedulable.

How many is too many

A practical ceiling for a solo project is the point where you can no longer name the critical path from memory — usually a few dozen tasks. Beyond that, groups should hide the detail: you review the milestone, and open the group only when its date moves. A WBS whose purpose is to be read in full is a document; a WBS whose purpose is to be computed is a schedule. You only get one of those.

How many tasks is too many?

When you stop being able to name the critical path. For a solo project a few dozen is usually the ceiling; beyond that, groups should hide detail.

Should the agent write the WBS?

It can draft one quickly, and that is useful. Review the edges and the estimates before you schedule anything — those two are where the optimism lives.
