How do I break an AI coding project into a WBS?

Break it down by what can be verified independently, not by what feels like a phase. The test of a good task is that someone can say whether it is done without reading the code.

Updated 2026-11-08 · by cygnus, the developer of KaidoPlan

The unit of breakdown: verification, not activity

Most WBS advice divides projects by activity — design, build, test, ship. That is a reporting structure, not a work structure. For a project executed by an agent, the useful unit is the smallest piece of work whose completion can be checked by a fact rather than an opinion: a route that responds, a migration that applies, a report that totals correctly.

Three rules follow:

  • If you cannot describe the check, the task is not small enough. "Improve the importer" has no check; "import a 1PUX export with attachments and reconcile the item count" does.
  • Separate planning from execution in the structure. The estimate is a human judgement; making the agent produce both the task and its duration is how plans become optimistic.
  • Model groups and milestones, not just tasks. Groups carry the hierarchy reviewers need; milestones are the points where someone other than the author has to agree.

A shape that works

  1. Acceptance criteria first. What has to be true on the delivery date, in observable terms.
  2. Chains that end at a milestone. Group tasks so each group produces one verifiable milestone, then connect the milestones.
  3. Integration and review as their own tasks. They are the ones that get eaten when the plan is compressed, and they are the ones whose loss shows up as a late project.
  4. Effort estimates in hours or days, per task. Coarse is fine; absent is not, because without estimates there is no schedule to compute.

Getting it into the tool

If the breakdown already exists as a nested outline, import it rather than retyping: wbs_import turns a nested task tree into the plan. Then add the dependencies — that step is where the real design work happens, because a WBS without edges cannot produce a critical path.

kaidoplan wbs import --file plan.kaido
kaidoplan schedule compute --file plan.kaido

The failure to avoid

An agent generates sixty tasks in a flat list with no dependencies and no estimates. It looks like thorough planning and it is unusable: nothing can be scheduled, nothing can be checked, and the only thing it supports is the illusion that the project is understood.

Questions this page does not answer

How many tasks is too many?

When you stop being able to name the critical path. For a solo project a few dozen is usually the ceiling; beyond that, groups should hide detail.

Should the agent write the WBS?

It can draft one quickly, and that is useful. Review the edges and the estimates before you schedule anything — those two are where the optimism lives.
