What is a critical path, and why does an AI project need one?

The critical path is the longest chain of dependent work in the plan. Its length is the project's duration, and every task on it has zero slack — delay one by a day and the delivery date moves by a day.

Updated 2026-11-16 · by cygnus, the developer of KaidoPlan

The definition, without the mystique

Take the dependency graph. For every task, compute the earliest it can start and finish, then the latest it can start and finish without pushing the project end. The difference between the two is slack. Tasks with zero slack sit on the critical path, and they form one or more chains from the start of the project to its end.

Two consequences follow, and they are the whole practical value:

  • The end date is not the sum of all estimates. It is the length of one chain. Adding a person to a task off the chain buys you nothing.
  • Any date change on the chain moves the delivery date one-for-one. That is the only set of tasks where "we lost a day" is literally true.

Read the two columns that decide everything:

  • Project duration is 11, from chain A → B → D → E. Not 2+5+4+3+1 = 15.
  • C has one day of slack. It can slip a day without moving the end date, and it is the only task where that is true. Everything else in the plan is the date.

This is the arithmetic that a green task list cannot express. Five tasks done is a count; the number that decides the delivery is the zero-slack chain, and it does not change because the count went up.

Why AI-assisted projects need it more, not less

An agent executes quickly and reports honestly, so the plan fills with completed work — and the natural conclusion is that the project is going well. Two mechanisms inflate that impression while the chain is unchanged:

  • Compressed estimates. An agent asked how long a task will take answers with an average case and no memory of the last time this class of task went wrong. Across forty tasks the optimism does not average out, because every task inherits the same missing memory.
  • Execution order instead of graph order. Work starts when it is asked for, not when its predecessor finishes. Every individual status stays true; the dates stop agreeing.

A checklist cannot see either one, because a checklist has no edges. The number that matters is not "how many tasks are done" but "how many days of zero-slack work remain".

Computing it

kaidoplan schedule compute --file plan.kaido
kaidoplan schedule path --file plan.kaido

The first runs the forward and backward passes and writes the dates. The second returns the tasks whose total slack is within the requested limit, together with the schedule. In the app the same chain is highlighted in the Gantt chart. All three read the same dependency graph, so they cannot disagree.

If you want to do the arithmetic yourself before trusting a tool, the free browser calculator takes tasks, durations and dependencies and shows ES, EF, LS, LF and total float with the zero-slack chain highlighted.

Four practical rules

  1. Review the critical path, not the task list. A standup that asks everyone for status optimises the wrong set. Ask what moved on the chain.
  2. Keep the chain short on purpose. Parallelising off-chain work is cheap; serialising on-chain work is what makes a plan fragile.
  3. Recompute after every change. The chain moves. Work that had slack last week can become the constraint this week, silently.
  4. Guard the edges, not just the numbers. A missing dependency compresses the schedule and looks healthy. If you cannot express "B cannot start until A finishes" such that a machine complains, the critical path you compute is a guess.

What a critical path does not tell you

It does not tell you whether the plan is achievable — a chain can be internally consistent and still too short. It does not shorten itself; it tells you which chain to cut, parallelise, or renegotiate, and the decision stays with you. And it does not replace a conversation with a client. It makes the slip visible on the day it happens instead of the week it becomes undeniable.

Questions this page does not answer

Do I need to understand the algorithm to use it?

No. You need to trust the graph, which means every dependency you assert has to be real. A wrong edge produces a confidently wrong critical path.

What is the difference between the critical path and the finish date?

The finish date is the output. The critical path is the explanation: which tasks, in which order, produce that date.
