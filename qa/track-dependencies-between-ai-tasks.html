How do I track dependencies between tasks an agent executes?

Record them as data in the plan file, not as instructions in a prompt. A dependency stated in chat survives one session; an edge in the plan survives the session, can be checked, and produces a date.

Updated 2026-11-17 · by cygnus, the developer of KaidoPlan

Two kinds of constraint, one place to keep them

Projects confuse two things that both affect dates but behave differently:

  • A dependency is structural: the acceptance test cannot run before the endpoint exists. It propagates dates and it creates the chain.
  • A constraint is a calendar fact: the security review cannot start before the 12th because the reviewer is away. It does not propagate; it clips.

Both belong in the plan, and both have a written form. What does not belong is either one living only in a message.

FormExampleEffect on the schedule
Finish-to-start (fs)Client integration starts when the server task endsPropagates the finish date downstream; creates the chain
Start-to-start (ss)Docs writing starts when the API design starts, one day laterLinks starts; the pair can overlap
Finish-to-finish (ff)Load test cannot finish before the last migration finishesLinks finishes without forcing a start order
Lag on an edgeTwo days of cooling-off after the buildAdds time to the edge, not to the task
Constraint: start no earlier thanReview cannot begin before 2026-12-12Delays the task; can push the end date
Constraint: end no later thanA demo that cannot slipTurns a slip into a reported conflict instead of a surprise

Three tests for whether an edge is real

Most bad schedules are not missing edges. They are invented ones — and an invented edge is worse than a missing one, because it changes the critical path while looking like rigour.

  1. Can you say it as a sentence with "cannot"? "The migration cannot start before the schema freeze." If the sentence is "it would be better if", it is a preference, and preferences belong in notes.
  2. Does work actually wait? An edge means a task sits idle until another completes. If a task could plausibly start and be corrected later, it is not blocked; it is coupled, which is different.
  3. Would removing it change the date? Not always — plenty of real edges are off the critical path. But if removing it changes nothing and nobody can name who waits, the edge is decoration.

Lag is not a task

Two days of review after a build can be modelled two ways, and the choice changes who is accountable:

  • As a lag (--dep <build-id>:fs:2): the edge carries two days. The schedule is right and the review is invisible. Nobody is assigned, nothing can be marked done, and no report mentions it.
  • As a task with a duration of two days: the review appears in the WBS, gets an owner, can be blocked, and shows up in the critical path when it becomes the constraint.

Use lag for time that is genuinely passive — a bake period, a vendor turnaround you cannot influence. Use a task for anything a person or an agent has to do. The tell is simple: if someone could be late, it is a task.

Why a prompt is the wrong storage

"Do the API first, then the client" works for one session and then stops existing. Concretely, over two sessions:

  1. Session one is told the order and complies. The transcript records the instruction.
  2. The session ends. The next one opens with a summary — "API done, moving to client" — which preserves the sequencing as a fact but not as a constraint.
  3. Session two hits a blocked API endpoint, so it starts the client work in parallel and fixes the mismatch later. Every individual status is true. The plan is now inconsistent with the order it was supposed to follow.

An edge in the plan survives step 2, and — the part that matters — the scheduler can prove the resulting dates are consistent with it. That proof is the entire difference between a plan and a description of a plan.

# the edge: client integration cannot start before the server task finishes
kaidoplan task update 9B44 --dep 4A1C:fs --file plan.kaido

# the constraint: the review cannot begin before 12 December
kaidoplan task update C710 --constraint startNoEarlierThan:2026-12-12 --file plan.kaido

# now make the schedule answer for it
kaidoplan schedule compute --file plan.kaido
kaidoplan violations --file plan.kaido

--dep takes <predecessor>[:type[:lag]], defaults to fs with no lag, and repeats, so one command can add several predecessors. Identifiers accept a unique prefix. Both flags work on task add as well, which is the better habit: create the task with its edges rather than adding them later from memory.

What a cycle looks like, and why it is reported

A cycle means a piece of work can never start, because starting it requires finishing it. Two ways this appears in real plans: a template copied twice, and a dependency added during a parallelisation pass that points backwards into the chain.

The failure is correct behaviour, not a bug: the schedule cannot be computed, and the cycle is named as a violation. What you must not do is delete the edge that is hardest to justify and move on — a cycle usually means two tasks were merged conceptually and one of them should not exist.

Beyond cycles, violations name the four classes of inconsistency a status report cannot see:

  • Negative slack: a constraint cannot be met by the current plan, so the deadline is already broken.
  • Constraint against dependency: the calendar says "not before the 12th" and the network says "must finish by the 10th". One of the two inputs is wrong.
  • Window violations: a task scheduled before the project start or after its end.
  • Manual start conflicts: a pinned date that contradicts the graph.

Practical discipline

  • One edge, one reason. If you cannot state why it exists, delete it. This is the single cheapest improvement available to most plans.
  • Do not model "related to". Undirected relations are not dependencies and add noise to every downstream number.
  • Guard the edges, not the dates. Pinning dates hides the problem; getting the edges right lets the date be computed, and a computed date can be defended in a review.
  • Re-check after parallelising. Splitting work changes the graph. The chain you knew last week may no longer be the constraint, and the new one is usually the integration step nobody scheduled.
  • Keep the graph in the repository. The plan is a file, so the dependency structure is reviewable in a diff — the only way a second person can audit it without reading a dashboard.

Questions this page does not answer

Can an agent add dependencies itself?

Yes, through the write tools, on a Pro licence after the trial. Whether it should is a policy question: edges change the delivery date, so many teams keep them human-owned.

What happens if I create a loop?

The schedule cannot be computed, and the cycle is reported as a violation. That is the correct failure: a loop means a piece of work can never start.
